MCP-методы DamuBPM: mcp_method, mcp_object, mcp_method_role

Публикация функций платформы для ИИ-клиентов по протоколу MCP: таблицы, обработчик, контракт БП, роли, добавление метода.

Как платформа DamuBPM публикует свои функции для ИИ-клиентов (Claude, ChatGPT, Cursor и др.) по протоколу MCP: таблицы настройки, REST-обработчик, контракт бизнес-процесса, роли, порядок добавления метода и типовые ошибки. Основано на коде REST mcp, mcp_oauth, модуле mcp_oauth_common и данных стенда test-helpdesk (07.11.2026: 77 методов, 187 параметров, 7 объектов, 2 инструкции).

Главная идея: MCP-метод — это запись в mcp_method, которая указывает на бизнес-процесс. Параметры метода (mcp_method_input, mcp_object) превращаются в JSON Schema инструмента, роли (mcp_method_role) решают, кто видит и вызывает метод. При вызове REST mcp запускает БП, передаёт ему весь JSON-RPC запрос в переменной input и возвращает клиенту текст из переменной result.

1. Как проходит запрос

ИИ-клиент (JSON-RPC 2.0, POST)
   │  Authorization: Bearer <токен платформы>       → /restapi/services/mcp/mcp
   │  Authorization: Bearer mca_<64 hex> (OAuth)     → /restapi/services/mcp/mcp_oauth
   ▼
REST mcp_oauth (только для OAuth) ── проверка токена, rate limit, JSON-RPC,
   │                                 is_disabled → выполняет тело REST mcp
   ▼
REST mcp
   ├─ пишет запрос в mcp_log, Commit()
   ├─ собирает instructions из mcp_instruction (по ролям пользователя)
   ├─ initialize / server/discover → версия протокола, instructions
   ├─ tools/list  → mcp_method (+ mcp_method_input, mcp_object_attr) по mcp_method_role
   └─ tools/call  → mcp_method.bp_process_id → BPMSStartProcess(код БП, user_id, {input = JSON запроса})
                                                    ▼
                                         БП: StringToJson(var.input).params.arguments
                                             → логика → var.result (строка)
   ◄── result.content[0].text = var.result
   └─ пишет ответ в mcp_log (outp = 1)

Колонка Смысл
mcp_method_id метод
param имя свойства в arguments

is_array 1 — массив ({type: "array", items: …})

mcp_method_role — кто видит и вызывает

Колонка Смысл
mcp_method_id, role_id метод × роль

mcp_object / mcp_object_attr — схема вложенного объекта

Таблица Колонки
mcp_object code (уникален без учёта регистра), title
mcp_object_attr mcp_object_id, attr (имя свойства), title (→ description), datatype_id, rq, is_array, object_id (вложенный объект), code

mcp_instruction / mcp_instruction_role

mcp_log

data (text, JSON запроса или ответа), outp (1 — ответ), created_at. Пишется на каждый запрос, без очистки (на стенде 66 МБ с 23.09.2026).

4. tools/list — как строится список инструментов

  1. Методы: coalesce(is_disabled, 0) = 0 и есть mcp_method_role с ролью из user_roles пользователя. Роль admin здесь не даёт доступ автоматически — нужна строка в mcp_method_role.
  2. Параметры: mcp_method_input inner join mcp_datatype, порядок по id.
  3. Схема параметра: - string / boolean → {type, description}; - object → {type: "object", properties, required} из mcp_object_attr объекта object_id; вложенность до 10 уровней, циклы обрываются; - is_array = 1 → {type: "array", items: <схема>}; - rq = 1 → имя в required.
  4. description параметра = все инструкции пользователя + "Описание метода: " + mcp_method_input.dscr. Поэтому у каждого параметра в клиенте видна приписка «Ты разработчик платформы DamuBPM…».
  5. inputSchema = {type: "object", properties, required, additionalProperties: false}.
  6. В инструмент добавляются securitySchemes: [{type: "oauth2", scopes: ["mcp"]}] (и в _meta).
  7. В ответе ttlMs = 60000, cacheScope = "private". initialize объявляет tools.listChanged = true, но уведомления об изменении списка сервер не отправляет — новый метод клиент увидит после переподключения.

Пример получившейся схемы (create_crontab):

{
  "name": "create_crontab",
  "title": "Создать задачу в планировщике заданий",
  "description": "Создает задачу в планировщике заданий по коду с lua скриптом…",
  "inputSchema": {
    "type": "object",
    "properties": {
      "code": {"type": "string", "description": "<instructions>Описание метода: Уникальный код задания"},
      "is_active": {"type": "boolean", "description": "<instructions>Описание метода: Включить или выключить."}
    },
    "required": ["code", "title", "croninterval", "script", "module_code", "is_active"],
    "additionalProperties": false
  }
}

5. tools/call — как вызывается метод

  1. mcp_user_id = request.user_id. Нет пользователя → HTTP 401, WWW-Authenticate: Bearer resource_metadata="…/.well-known/oauth-protected-resource/restapi/services/mcp/mcp", scope="mcp".
  2. Поиск: mcp_method.code = params.name + роль пользователя в mcp_method_role → bp_processes.code.
  3. BPMSStartProcess(код_БП, mcp_user_id, { input = JsonToString(request.input) }) — в БП приходит весь JSON-RPC запрос.
  4. Ответ клиенту — всегда result.content = [{type: "text", text: …}]:
Ситуация text isError
bpErrNum ≠ 0 (исключение, ошибка SQL в БП — «Critical Error! Transaction RollBack…») Ошибка выполнения метода: <errText> true
БП завершился, result пустой Метод не вернул результат true
БП завершился, result заполнен значение result как есть false
метод не найден или нет роли Метод не найден или нет доступа: <name> true
  • last_error обработчик не читает. Если БП записал ошибку только в result («Ошибка: …») или в last_error, клиент получит isError = false. Ошибку для модели нужно писать в result понятным текстом или JSON {ok:false, error}.
  • Через mcp_oauth до вызова дополнительно проверяется is_disabled = 0 (иначе JSON-RPC ошибка -32602 Unknown or disabled tool), разрешены только initialize, server/discover, tools/list, tools/call, ping; тело запроса до 4 МБ, 180 запросов в минуту с IP.

6. Контракт бизнес-процесса

Все 77 методов стенда устроены одинаково:

Что Значение
Тип БП businessprocess, модуль обычно core, код mcp_method_<имя>
Переменные input (jsonb, входная), result (longtext, выходная), last_error (varchar, выходная)
Схема Start → ScriptTask → XOR → End «Успех» (var.last_error=="") / End «Ошибка» (var.last_error~="")
Шаблоны на стенде mcp_method_get_template (запись), mcp_method_list_template (список), mcp_method_create_update_template (создание/изменение) — is_template = 1

Что лежит в var.input

{
  "jsonrpc": "2.0",
  "id": 12,
  "method": "tools/call",
  "params": {
    "name": "c_ai_booking_create",
    "arguments": {"master_id": "3", "service_id": "7", "date": "2026-11-10", "start_time": "11:00"}
  }
}
  • boolean приходит Lua-логическим значением, массив — таблицей, объект — таблицей.
  • string-параметры, которые по смыслу числа, переводить tonumber и проверять.
  • sys.user_id в БП = пользователь MCP-подключения.

Рекомендуемый скрипт (по образцу c_ai_*)

var.last_error = ""
var.result = ""
local function fail(msg)
  var.last_error = tostring(msg)
  var.result = JsonToString({ok = false, error = var.last_error})
end

local req = StringToJson(var.input)
local a = (type(req) == "table" and type(req.params) == "table" and req.params.arguments) or {}
if type(a) ~= "table" then fail("arguments должен быть объектом") return end

local id = tonumber(a.id)
if not id or id < 1 or id ~= math.floor(id) then fail("id: целое число > 0") return end

local errText, errNum = CheckGrantOfEntity(sys.user_id, "its_cli_contract", "is_detail_view", id)
if errNum ~= 0 then fail("Нет доступа к записи") return end

local row, e, n = SqlQueryRow2([[select id, code, title from its_cli_contract where id = ?]], id)
if n == 2 then fail("Запись не найдена") return end
if n ~= 0 then fail(e) return end

var.result = JsonToString({ok = true, item = row})

Правила: - Ответ — компактный JSON: только поля, нужные модели; списки — через array(), с limit/offset. - Не вызывать Commit()/Rollback() в скрипте БП. - Ошибку SQL лучше ловить по errNum и отдавать через fail; необработанная ошибка SQL роняет весь БП (откат, isError = true). - Методы, которые меняют метаданные платформы, после записи вызывают ClearCache() (или dbrequire("pkg/cache").clearCacheHosts()) и dbrequire("pkg/mcppatch").process({entity_code=…, pk=…, user_id=sys.user_id}). - SqlQueryRows/SqlExec2 ограничения видимости не применяют: права на записи проверять CheckGrantOfEntity или условием в SQL.

7. Инструкции mcp_instruction

  • В initialize и server/discover поле instructions = склейка instructions всех записей, у которых в mcp_instruction_role есть роль пользователя (через \n\n).
  • Тот же текст приписывается к описанию каждого параметра в tools/list (п. 4).
  • На стенде: damubpm (роль mcp_user) — «Ты разработчик платформы DamuBPM. Используй локальный навык damubpm development…»; mcp_seller_example (роль mcp_seller_example) — «Ты продажник продукта DamuBPM…».
  • Инструкцию держать короткой: она повторяется столько раз, сколько параметров у доступных методов (на стенде 187).

8. Роли и доступ

Три независимых слоя:

Слой Где Что решает
Подключение токен платформы или OAuth-токен кто пользователь (request.user_id)
Метод mcp_method_role виден ли метод в tools/list и можно ли его вызвать
Данные код БП: CheckGrantOfEntity, условия SQL какие записи метод читает и меняет
  • Роли на стенде: mcp_user (69 методов разработчика, 2 пользователя: 1 — admin, 89 — не admin), mcp_seller_example (8 методов c_ai_*, 1 пользователь).
  • bp_process_roles у БП методов заполнены несогласованно: у части только admin (например, mcp_method_db_get_query, mcp_method_add_pages_ui_blocks_n, все flt_*), у mcp_method_get_angular_widget ролей нет. Проверяет ли BPMSStartProcess эту таблицу при вызове из REST, на стенде не проверено. Для новых методов выдавать роль и в mcp_method_role, и в bp_process_roles (can_run = 1) и проверять вызов под не-admin.
  • Методы разработчика (db_execute_sql, create_rest_service, create_crontab и др.) дают полный доступ к базе и коду. Роль mcp_user выдавать только разработчикам; для внешних ИИ-агентов заводить отдельную роль с узкими методами (как mcp_seller_example).

Актуальный список:

select m.id, m.code, m.title, p.code bp, coalesce(m.is_disabled, 0) dis,
       (select string_agg(r.code, ',') from mcp_method_role mr join roles r on r.id = mr.role_id
         where mr.mcp_method_id = m.id) roles,
       (select string_agg(i.param || case when i.rq = 1 then '*' else '' end || ':' || d.code
                          || case when i.is_array = 1 then '[]' else '' end, ', ' order by i.id)
          from mcp_method_input i join mcp_datatype d on d.id = i.datatype_id
         where i.mcp_method_id = m.id) params
from mcp_method m left join bp_processes p on p.id = m.bp_process_id
order by m.id;

11. Как добавить новый метод

11.1. Спроектировать

  • Имя: латиница, _, без пробелов, с префиксом модуля (its_contract_get). Код БП: mcp_method_<имя>.
  • Одна задача на метод. dscr пишет когда вызывать, что вернёт, ограничения («создавать запись только после согласия клиента»).
  • Параметры: минимум обязательных, числа — string с проверкой в БП, сложная структура — через mcp_object.

11.2. Создать БП

Вариант A — через MCP: create_bp_process с bp_processes_code_template = mcp_method_get_template / mcp_method_list_template / mcp_method_create_update_template, затем get_bp_process_details (найти код ScriptTask) и update_bp_points_script␣. Копирование шаблона этим методом в этой сессии не проверялось — после создания сверить переменные input/result/last_error и условия на стрелках.

Вариант B — вручную в конструкторе по таблице п. 6.

11.3. Зарегистрировать метод (одним запросом)

with m as (
  insert into mcp_method (code, title, dscr, bp_process_id, is_disabled)
  select 'its_contract_get', 'Договор клиента по id',
         'Возвращает номер, даты и сумму договора клиента по его id. Вызывать, когда пользователь спрашивает о конкретном договоре.',
         p.id, 0
  from bp_processes p where p.code = 'mcp_method_its_contract_get'
  returning id
), i as (
  insert into mcp_method_input (mcp_method_id, param, rq, datatype_id, is_array, dscr, code)
  select m.id, x.param, x.rq, d.id, 0, x.dscr, uuid_generate_v4()
  from m cross join (values ('id', 1, 'string', 'ID договора (число)')) x(param, rq, dt, dscr)
  join mcp_datatype d on d.code = x.dt
  returning id
), r as (
  insert into mcp_method_role (mcp_method_id, role_id)
  select m.id, ro.id from m cross join roles ro where ro.code = 'mcp_user'
  returning id
), br as (
  insert into bp_process_roles (process_id, role_id, can_run)
  select p.id, ro.id, 1 from bp_processes p cross join roles ro
  where p.code = 'mcp_method_its_contract_get' and ro.code = 'mcp_user'
    and not exists (select 1 from bp_process_roles x where x.process_id = p.id and x.role_id = ro.id)
  returning id
)
select (select id from m) method_id, (select count(*) from i) inputs,
       (select count(*) from r) roles, (select count(*) from br) bp_roles;
  • Через db_execute_sql запрос передаётся в Base64; в литералах нельзя ? и $1 (см. навык, MCP-инструменты).
  • mcp_method_input.code при SQL-вставке заполнять самому: entityEvent mcp_method_input_upsert срабатывает только при сохранении через платформу.
  • Параметр-массив объектов: datatype = object, is_array = 1, object_id = id объекта из mcp_object.

  local vars, inst, task, errText, errNum = BPMSStartProcess("mcp_method_its_contract_get", 89, {input = JsonToString(req)})

13. OAuth 2.0

  • Поток: mcp_oauth_register (публичный клиент, без секрета) → mcp_oauth_authorize (GET, PKCE S256, cookie __Host-damubpm_mcp_oauth) → страница mcp_oauth_consent (вход пользователя, согласие) → mcp_oauth_token (authorization_code, refresh_token) → вызовы mcp_oauth с Authorization: Bearer mca_<64 hex>.
  • Логика в SQL-функциях public.mcp_oauth_* (begin_authorization, consent_action, exchange_token, token_action, client_action, issue_tokens и др.), Lua — только HTTP-адаптер (mcp_oauth_common): заголовки безопасности, CORS, лимиты RateLimiter, разбор form/JSON.
  • Токен в строке запроса (?access_token=) отклоняется (400). Scope один — mcp.
  • Таблицы: mcp_oauth_clients (на стенде 27), _requests, _codes, _grants (активных 7), _tokens, _settings, _test_runs; самопроверка — модуль mcp_oauth_selftest.
  • Доступные методы при OAuth определяются теми же mcp_method_role по user_id из разрешения.

15. Подводные камни и замечания

  1. Ошибки как успех. REST смотрит только на bpErrNum и пустой result. «Ошибка: …» в result или заполненный last_error уходят с isError = false. Писать ошибки так, чтобы модель их поняла из текста ({ok:false,error}).
  2. is_disabled при прямом подключении. Через mcp (токен платформы) tools/call выключенный метод не проверяет: он исчезает из списка, но вызывается, если клиент знает имя. Через mcp_oauth проверка есть. Чтобы метод точно не работал — убрать его роли или БП.
  3. Пробелы в кодах. У 5 методов код с пробелом в начале или конце (mcp_method_create_query, mcp_method_get_luas, update_bp_points_script, get_bp_process_list, dashboards_del_page). Клиенты переименовывают их (_…, …_), не все клиенты сопоставляют имя обратно. Новые коды — без пробелов.
  4. Инструкция в каждом параметре. Текст mcp_instruction повторяется в описании каждого параметра → большой tools/list. Держать инструкцию короткой.
  5. Нет типа number. Только string, boolean, object. Числа — строкой с tonumber и проверкой диапазона в БП.
  6. Параметр без типа пропадает. mcp_method_input соединяется с mcp_datatype через inner join: без datatype_id параметр не попадёт в схему (сейчас таких 0).
  7. Список не обновляется сам. listChanged = true объявлен, но уведомлений нет; после добавления метода переподключать клиента.
  8. Права на данные — в БП. mcp_method_role открывает метод, а не записи. SqlQueryRows ограничений не применяет.
  9. db_execute_sql выполняет любой SQL (включая DDL) от имени платформы, возвращает только первый результат; при ошибке выполнения SQL внутри БП — «Critical Error! Transaction RollBack…». Не выдавать роль с этим методом внешним агентам.
  10. Журнал хранит заголовки. mcp_log.data содержит запрос целиком, включая Authorization с токеном. Таблица растёт без очистки (66 МБ за 1,5 месяца). Ограничить доступ к mcp_log, маскировать заголовок и чистить старые записи.
  11. bp_process_roles несогласованы с mcp_method_role (п. 8). Выдавать обе и проверять под не-admin.
  12. Роль admin не видит методы без строки в mcp_method_role.
  13. Большие ответы. Весь result уходит в контекст модели; отдавать только нужные поля, ставить лимиты по умолчанию (c_ai_services_list: 20, максимум 100).
